# <Project> agent policy

This file is the single binding policy for every agent that works on this repository, on
either provider. It changes only through an entry in `execution/decisions/` that names the
section changed and the date. Every other instruction file (`CLAUDE.md`, the agent
definitions, the prompt templates, operations notes) implements this file; where they
differ, this file wins. Last policy change: <date>.

## 1. Reading sets by role

Orientation text is the largest recurring token cost in a repository. Each role reads
exactly its row and nothing else. Product handoff documents are for people; no agent opens
them. A dispatch prompt that asks an agent to read outside its row is wrong.

| Role | Read | Never read |
|---|---|---|
| Worker (fast, default and deep lanes on either provider) | Sections 2, 4, 5 and 6 of this file; the packet `execution/tasks/<ID>.md`; the specification sections and `execution/decisions/` entries the packet names; the dispatch prompt built from `templates/TASK_PROMPT.md` | product handoff docs, operations notes, `execution/RESUME_STATUS.md`, `execution/history/`, `docs/evidence/`, other packets |
| Reviewer | `templates/REVIEW_PROMPT.md`; sections 5 and 6 of this file; the packet; the diff; the run's `manifest.json` | the same as workers |
| Integrator (one session per wave) | this file; `execution/tasks.json`; `execution/guidance/`; the Now block of `execution/RESUME_STATUS.md`; the output of `agent-progress`; the lease entries of packets it touches; the packets it dispatches; the diffs it integrates | during a wave: handoff docs, `execution/history/`, `docs/evidence/`, operations notes |
| Creator | `README.md`, `execution/guidance/README.md`, `agent-progress` output, `.agent-waves/WAVES.md` | — |

## 2. Authority and records

The integrator owns shared schemas, root manifests and lockfiles, migrations, top-level
assembly and every record below. Workers own only their leased paths and request everything
else through a contract-change request (section 5).

| Record | Holds | Written by | When |
|---|---|---|---|
| `execution/tasks.json` | Task graph and packet status: `planned`, `implementing`, `done` | Integrator | Status transitions below |
| `execution/tasks/<ID>.md` | One packet's scope, owned paths, acceptance | Creator or integrator, before dispatch | Scope changes, with a decision entry when acceptance changes |
| `execution/leases.json` | Who holds which paths, branch, base SHA, runtime profile, `remaining` work | Integrator | Lease created, updated each wave, closed at integration |
| `execution/RESUME_STATUS.md` | The Now block: root HEAD, the one next packet, open leases in a line each, blockers. At most 25 lines | Integrator | Every wave |
| `execution/history/` | One short entry per wave: what was integrated, what remains | Integrator | Every wave |
| `execution/TASK_BOARD.md` | Human view of `tasks.json`, generated by `agent-board` | Tool | Never edited by hand |
| `execution/decisions/` | Decisions that change scope, contracts, acceptance or this policy | Creator or integrator | When a wave stops for a decision |
| `execution/guidance/` | Creator steering: `PRIORITY.md` dispatch order, loop defaults | Creator | At will |
| `docs/evidence/<run>/` | `README.md`, `manifest.json`, `samples/`; raw captures stay local | Worker or integrator | With the work it proves |

Status moves only by the integrator: `planned` to `implementing` when the packet gets its
first lease; `implementing` to `done` only in the integration commit that lands the packet's
full acceptance with review evidence. A partial integration leaves it `implementing`. A
defect in a done packet is a new fix lease under the same ID; a wrong acceptance is a
decision entry. `agent-progress` reports packets whose status and lease state disagree;
`agent-admin` fails when any record is inconsistent, and `agent-wave` refuses to start on it.

## 3. Roles, lanes and limits

**Integrator.** One session at high effort per wave. It collects finished lanes, integrates
reviewed packets serially, dispatches, records and stops (section 7). It does not
implement. Higher effort is reserved for a decision turn: freezing or changing a shared
contract, a gate verdict, reconciling conflicting reviews, or writing a decision entry.

| Lane | Provider A agent / effort | Provider B agent / effort | Eligible work |
|---|---|---|---|
| Fast | `<name>`, low | `<name>`, medium on a small model | Mechanical, fully specified work a test or review would catch. A fast worker that meets a design decision stops and reports it. |
| Default | `<name>`, medium | `<name>`, medium | A settled packet with clear acceptance. |
| Deep | `<name>`, high | `<name>`, high | New or changed contracts, scheduling or recovery semantics, provider and media integration. |
| Review | `<name>`, high, read-only | `<name>`, read-only | Independent review by an agent that did not write the change. |

When unsure between two lanes, take the higher for anything touching shared contracts or
state authority and the lower for anything with a test that would catch the mistake.

**Limits.** <N> active workers normally, <M> for independent bursts, across both providers,
reviewers included. These are ceilings, not targets. Children never dispatch further agents.
Provider settings do not enforce the combined limit; the integrator does.

**Provider balance.** The cheaper plan is the default worker. The scarcer plan's slots are
assigned first at every wave from the pacing block the supervisor supplies (`agent-pacing`).
The dispatch record carries the slot count and, when zero, exactly one waiver reason:
quota-blocked, no eligible packet, or not a wave. Fill a scarce slot in this order: a pending
independent review; judgment-heavy packets (UI, design); any packet that failed review
twice; otherwise any ready packet with disjoint paths.

**Independent review** precedes integration of any substantial implementation. The reviewer
never authored the change; a different model alone is not proof of independence.

## 4. Isolation and environment

One branch and one worktree per task, created by the integrator at the pinned merged
prerequisite SHA. A worktree is a separate checkout sharing git history; it is not a sandbox
and does not allocate ports, databases or storage. Each task also leases a runtime profile.
No shared mutable dependency directory. Verify branch and HEAD before editing. Never stop a
process by generic executable name. Keep credentials out of git, logs and job payloads.
Production code uses shell-free argument-array subprocess calls.

## 5. Contracts, merge and review discipline

A worker that needs a missing field or method submits a contract-change request: current
contract, proposed additive change, why, consumers affected, migration story, tests,
compatibility. The integrator merges the contract before other lanes build on it. Expand
schemas before removing fields. No local duplicate type bypasses a shared schema.

The reviewer checks diff scope, architecture boundaries, actual tests and negative cases. UI
is judged by operation through visible controls, not resemblance to a mockup. The integrator
merges serially, runs affected suites and keeps the integration branch usable. An
integration commit carries the trailers `Integrates: <taskId> <branch> <sha>` and
`Reviewed-by: <agent>`; `agent-guard` fails a commit that changes implementation code
outside the integrator-owned prefixes without them.

Completion distinguishes implemented, tested here, reviewed and untested target. A unit test
is not end-to-end evidence; an unrun test is never labelled passed.

## 6. Evidence

Evidence is actual tests, gestures through public controls, screenshots and rendered output.
A run directory under `docs/evidence/` commits its `README.md`, a `manifest.json` written by
`agent-manifest <dir>` and at most a handful of sampled captures under `samples/`. Raw
captures stay local and are gitignored. Cite artifacts by path and hash. Never claim a gate
passed without its evidence.

Every worker and reviewer hands back the same block:

```text
Task / base SHA / final commit:
Implemented behavior (or verdict, for review):
Changed paths:
Contracts consumed / changed:
Commands actually run and exact exit codes:
Evidence paths (manifest.json):
Negative cases tested:
Unsupported or untested environments:
Remaining risks:
Ready for review / integrate: yes or no, with reason
```

## 7. Integrator discipline

Sessions are waves, not threads. One integrator session performs one wave: collect finished
lanes, integrate at most one reviewed packet, dispatch the next lanes, record, stop.
`agent-wave` launches such sessions from `templates/WAVE_PROMPT.md` with the Now block,
progress, previous handoff, dispatch priority, pacing and guard output already filled in. A
session that has integrated one packet or reached its tool-call budget records state and
stops; the next wave starts with fresh context. Long goal threads are not used.

The supervisor computes pacing and the guard before the session starts and runs
`agent-admin` as preflight. The integrator never runs pacing or ledger tools, never runs
browser fixtures or views screenshots itself, and never reads history or evidence during a
wave. It edits only the integrator-owned prefixes plus `execution/`, `docs/` and tooling; a
needed code fix is dispatched to a worker.

**Cross-provider data authorization.** Both providers may send repository source, diffs,
